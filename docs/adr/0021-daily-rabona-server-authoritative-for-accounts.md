# 21. Daily Rabona becomes server-authoritative for signed-in accounts

Status: Accepted — implemented 2026-09-18. Extends the account/ranked model from [ADR 0006](0006-accounts-and-ranked-progress.md), [ADR 0007](0007-automatic-animal-aliases-and-optional-nicknames.md) and [ADR 0012](0012-ranked-ten-options-v2-ruleset.md); leaves the guest-only local Daily Rabona feature (`docs/plans/2026-09-17-daily-challenge.md`) untouched for signed-out play.

## Context

A player reported signing in and seeing zero games played despite having played that day's Daily Rabona. Investigation confirmed this was by design, not a bug: Daily Rabona has always been a fully local, device-only feature (`localStorage['derabona.daily.v1']`) with no connection at all to the account/ranked system - playing it while signed in records nothing server-side, and its local points/streak have never counted toward the public leaderboard.

The owner and the repo's other maintainer, who originally built Daily Rabona as local-only, agreed on three requirements for changing this:

1. Daily points should sum into the same public/general leaderboard total as career (ranked) points, but the two sources must stay distinguishable in storage - not silently merged into one ledger.
2. A server-side Daily streak (current and best) per account, queryable as its own leaderboard, separate from the points board.
3. Daily's player pool has no relationship to ranked's "already answered" exclusion: the same player can earn a career result and, independently, one or more Daily results over time, with no conflict.

Requirement 3 rules out the simplest-looking approach (add a `ruleset='daily'` value and insert into the existing `ranked_private.results`): that table's primary key is `(user_id,player_id,ruleset)`, encoding "once ever per player" - exactly the invariant that protects the career leaderboard from replay farming (ADR 0006). But Daily's schedule is a fixed, deterministic sequence of 220 slots that cycles forever (`docs/plans/2026-09-17-daily-challenge.md`'s "later days repeat the frozen 220-descriptor cycle"), so the same `player_id` legitimately recurs across different Daily dates roughly every 73 days. Sharing `results`'s uniqueness domain with Daily would eventually block Daily from crediting a repeat player, or (worse) collide with an already-recorded career result for that same player under a scheme never designed to allow two independent events for one player.

## Decision

**Fully independent storage, joined only at read time.** New tables under `ranked_private`, with no FK or uniqueness relationship to `rounds`/`results` at all:

- `daily_schedule(slot_index primary key 0-219, player_id, option_candidate_ids text[10])` - seeded once, verbatim, from the already-shipped, already-tested `DAILY_SCHEDULE_V1` literal embedded in `index.html`. Not regenerated: extracting the frozen client data byte-for-byte (via a one-time authoring script, `scripts/generate-daily-schedule-migration.mjs`) guarantees the server and every existing guest client agree on the same 220 slots/options by construction, with zero risk of the seeded-PRNG distractor logic drifting between two implementations. The seed migration asserts every `player_id` and every `option_candidate_ids` element resolves against `players`/`candidates` and aborts the whole transaction otherwise - array elements have no native foreign key, so this integrity check has to be explicit and fail-closed rather than left to a constraint.
- `daily_rounds(user_id, date, round_index 0-2, ...)`, primary key `(user_id,date,round_index)` - no extra partial-unique index is needed the way `ranked_private.rounds` needs one, because `date` is always the server's own current UTC date at insert time, never client-supplied, so the primary key alone guarantees at most one row per slot per day per user.
- `daily_results(user_id, date, round_index, player_id, points, correct, finished_at)`, primary key `(user_id,date,round_index)`, reusing the existing generic `ranked_private.immutable_result()` trigger function (it only raises `RESULT_IMMUTABLE`, no table-specific references, so no second copy was needed).
- `daily_streaks(user_id primary key, current_streak, best_streak, last_completed_date)`, upserted only when a day's third round reaches a terminal state.

**Combine at the leaderboard query, not the storage layer.** `ranked_private.leaderboard()`'s `scores` CTE now sums a `UNION ALL` of `results` (ruleset `v2`) and `daily_results`, joined to `memberships` exactly as before. `UNION ALL`, not `UNION`, is load-bearing: the same account can legitimately earn two separate scoring events for the same `player_id` (one career, one Daily), and a plain `UNION` would silently deduplicate them if the row tuples happened to coincide. The public response shape (`entries`/`own`/`total`/`competition`, and each entry's `{nickname,points,answered,correct,rank}`) is unchanged - `tests/ranked-backend.test.mjs` has exact `assert.deepEqual` checks against that entry shape, and every existing leaderboard test passes unmodified, since none of the existing fixtures create `daily_results` rows. This satisfies requirement 1's "sum into the general total" without adding a visible per-source breakdown to the public board; the origin is already unambiguous at the storage layer (two structurally distinct tables), and the account's own `dailyProgress` response carries the Daily-specific numbers (streak, today's rounds) separately. A visible per-row split on the public board, if wanted later, is a small, separately-scoped follow-up.

**No import of a signed-in user's already-in-progress local guest attempt.** This mirrors an already-shipped, already-tested precedent: Unlimited already tells a guest explicitly that their score "cannot be transferred after sign-in." Daily does the same - the first `dailyProgress` call for a newly-signed-in user creates three fresh server rounds regardless of what the local `DailyChallenge` attempt for that date already recorded; the local attempt is left untouched in `localStorage`, harmless and permanently unranked, exactly like a guest's Unlimited results today. A one-time dismissible notice on the Daily card tells the player this, the first time `DailyRankedUI` detects local progress for the current date. This avoids an entire class of "can the server trust client-reported prior progress" problems - the server never reads or accepts anything from the local document.

**One RPC, extended, not a parallel one.** Four new `action` values on the existing `public.ranked_game` function and `ranked-game` edge function, sharing its already-audited auth/idempotency/rate-limit machinery (the same function already serves a second `mode` for `account-delete`):

- `dailyProgress` - no idempotency key (it's a deterministic `on conflict do nothing` ensure-today's-rows call, handled in the same early branch as the existing `progress` action, before the idempotency machinery). No `dailyStart` action exists: unlike ranked's `start`, which makes a genuine one-shot random choice, which three players apply to any date is a pure function of the server clock - nothing to "start."
- `dailyHint` / `dailyAnswer` - addressed by `(date, roundIndex)` instead of a synthetic round id, since the primary key triple already identifies the row; `roundIndex`/`expectedVersion` replace `roundId`. A new `ROUND_LOCKED` error guards round order (0→1→2), which ranked's single-open-round model never needed to check.
- `dailyStreakLeaderboard` - handled in the same public/pre-auth branch as `leaderboard`, ranked by `current_streak desc, best_streak desc`. Accounts with a lapsed streak (`current_streak=0`, `best_streak>0`) still appear, so a broken personal best stays visible; this is a cheap, deliberately reversible choice (flip to `having current_streak>0` to hide lapsed streaks instead) rather than a settled one.

`ranked_private.projection()` (the response every ranked action already returns) is deliberately left untouched - it's on the hot path for every ranked mutation, and coupling it to Daily state for no benefit widens the blast radius of this change into heavily-tested, unrelated code. Daily gets its own `ranked_private.daily_projection()`, returned only by the four Daily actions above.

**Client**: guests get zero behavior change - every new code path is gated on `Accounts.session`, exactly like `RankedUI` already gates every ranked network call. A new `DailyRankedUI` module (living beside `RankedUI` in the same `game-ui` script block, reusing its DOM/render helpers) takes over the shared round panel only when `DailyUI.isDaily() && Accounts.session`, mirroring `RankedUI`'s own sync/mutate/accept/identity-guard shape and its single-round-trip mutation pattern (no local-optimistic scoring to reconcile, per [ADR 0013](0013-single-round-trip-ranked-mutations.md)'s precedent). Its "Next" button advances the locally-displayed round index without a network call, since the server already created all three rounds up front.

## Consequences

- Both new migrations are purely additive: no `ALTER` to `results`, `rounds`, `accounts`, `memberships`, `players`, `candidates`, `receipts` or `rate_limits`. The two `create or replace function` calls (`ranked_game`, `leaderboard`) are this codebase's established mechanism for evolving those functions via a new migration file, not an edit to an already-applied one.
- `answered`/`correct` in leaderboard/projection-style aggregates now count *scored attempts*, which can include the same `player_id` more than once for one account (once via career, potentially several times via Daily as the schedule cycles) - a real, intentional change from the prior "each player counts once" framing, corrected in `DESIGN.md` and `README.md` alongside this ADR so a future change doesn't "fix" the leaderboard query back to a once-per-player dedupe and silently break Daily scoring.
- Today's three players, their options and the correct answers are still fully present in the shipped `DAILY_SCHEDULE_V1`/`DAILY_PAYLOAD_V1` client JS, since guests need it for offline play. Going server-authoritative for signed-in accounts stops a client from *faking a reported score* (editing `localStorage`) but neither hides nor claims to hide the answer from someone reading page source - exactly as true before this change as after it.
- If the schema migration (`202609180001`) is ever applied to the hosted database before the seed migration (`202609180002`) in separate manual runs, `dailyProgress` handles a missing `daily_schedule` row for a slot by returning an empty rounds array rather than erroring, the same defensive posture ranked's own `start` action already takes when no eligible player remains.
- No guest/practice change of any kind for Daily Rabona - this ADR and its migrations touch the signed-in path exclusively; `tests/daily-challenge.test.mjs` (the guest-only local logic) needed no changes.
