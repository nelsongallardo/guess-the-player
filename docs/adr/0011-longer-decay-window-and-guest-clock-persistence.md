# 11. A longer decay window, and closing a guest-clock reload exploit

Status: Accepted — implemented 2026-09-14. Amends [ADR 0009](0009-speed-decay-anti-lookup-tightening.md); the grace window (2s) and floor value (25%) are unchanged, only the floor-time constant is retuned, alongside an unrelated but simultaneously-shipped fix to how the guest clock is sourced.

## Context

Two separate findings from real play, shipped together since both touch the same scoring clock.

**The 12s floor was too tight.** ADR 0009 picked 12 seconds specifically to make an outside lookup a bad trade. In practice it also made *honest* play feel rushed: reading a 10-option career (this project's guest/practice Hard deck) and choosing among ten names takes real time, and hitting the floor that fast turned "answer confidently" into "answer fast or lose most of the points regardless." The anti-lookup goal doesn't need a 12-second window specifically - it needs *any* window meaningfully shorter than round-tripping to a search engine and back, and 24 seconds still comfortably clears that bar.

**A guest reload reset the clock to zero.** Guest/practice's elapsed-time clock (`roundClockStart`) was deliberately *not* persisted - the documented reasoning (see ADR 0001/AGENTS.md) was "resuming shouldn't charge you for time spent away from the tab." But since guest gameplay state (the deck, guesses, hints) *is* persisted and survives a reload, while the clock was not, a player could open a round, take as long as they wanted (including looking the answer up on another device - exactly what ADR 0009 was built to discourage), then reload the page immediately before answering. `roundClockStart` reset to `Date.now()` on that reload, so the next elapsed-time read came back near zero - full marks, no matter how long the round had actually been open. This defeated ADR 0009's entire premise for guest/practice, the only mode where it was reachable (ranked's clock is the server's own `started_at`, never client-controlled, so it was never affected).

## Decision

**Floor time**: `SLOW_MS` in `CareerGame`'s `timeFactor` (`index.html`, `game-model`) goes from 12000 to 24000. Mirrored server-side via `supabase/migrations/202609140004_longer_speed_decay_window.sql` (`create or replace function ranked_private.points()`, the same append-only pattern every migration here uses rather than editing an already-applied one). `GRACE_MS` (2000) and `MIN_TIME_FACTOR` (0.25) are untouched. Every place that stated "12 seconds" as fact - the rules dialog's worked bar-chart example, the points FAQ in both languages, this codebase's own docs - is updated to 24; the bar-chart's illustrated values (100/63/25) are unchanged, since the midpoint of a linear decay lands on the same fraction (62.5%) regardless of how wide the window is - only its time label moved from "7s" to "13s".

**Guest clock persistence**: the guest round clock is now stored directly in `sessionStorage` under `touchline.clock.v1` as `{playerId, startedAt}`, read back and validated against the *current* round's player id on load (`loadRoundClock()` in `game-ui`). A reload of the same round restores its real `startedAt`, so elapsed time keeps counting exactly the way ranked's server clock already does. A genuinely new round (any real `resetRoundClock()` call - a fresh deck, Next Player, a competition switch, Reset, sign-out) still starts a clean clock, since it's keyed to that new round's own player id and every one of those call sites assigns `state` to the new round before calling `resetRoundClock()`. This key deliberately goes straight to `sessionStorage` rather than through `GuestStorage`: `GuestStorage.getItem`/`.setItem` write through to `sessionStorage` fine for any key, but its read side only hydrates its in-memory cache from `sessionStorage` once, at construction, for its own hardcoded legacy-migration key list - a key outside that list would read back `null` on every fresh page load (i.e. every reload) even though it was saved correctly, which is exactly the bug this ADR is closing. Discovered by writing a real-browser reload test rather than trusting the read-through assumption, and worth remembering: `GuestStorage` is not a generic key-value store despite its `getItem`/`setItem` shape - it's a migration-bookkeeping helper for exactly four hardcoded keys, and any *new* persisted key belongs in `sessionStorage` directly.

This directly supersedes the "resuming does not charge time away" framing in ADR 0001/AGENTS.md: that was written to protect a player from being penalized for a *long, real* absence (closing the tab, coming back tomorrow), not to let anyone reset the clock at will. Persisting the real start time serves the original protective intent just as well (a genuine long absence still only ever grazes the 25% floor, never scores literally zero) while removing the reload loophole entirely.

## Consequences

- No new backend field or ranked schema change - ranked was never affected by the reload issue and needed no client-side clock fix, only the same floor-time retune as guest.
- `tests/model.test.mjs`'s scoring test, `tests/points-faq.test.mjs` (both the literal-string checks and the worked-example computation), and the SQL/JS parity sweep in `tests/ranked-backend.test.mjs` are updated to the new floor time; the sweep's sample elapsed values were re-checked against the new curve for accidental exact-.5 rounding coincidences (the same class of test flakiness that came up when ADR 0009 first shipped) and adjusted where needed.
- Like every schema migration here, pushing `202609140004_longer_speed_decay_window.sql` to `main` only deploys the static site - applying it to the live database is a separate, deliberate step (the CLI or `supabase-deploy.yml`; see `docs/leaderboards.md`).
- The guest clock persistence fix has no user-visible UI change and needs no migration; it's a pure `game-ui` fix, live as soon as `index.html` deploys.
