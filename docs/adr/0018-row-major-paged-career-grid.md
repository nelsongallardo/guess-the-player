# 18. Row-major paged career grid, replacing the column-major two-row attempt

Status: Accepted — implemented 2026-09-15. Supersedes [ADR 0017](0017-desktop-two-row-career-cap.md).

## Context

ADR 0017 capped the desktop career grid at two rows using `grid-auto-flow:column`: each column filled top-to-bottom (a "pair" of two chronological clubs) before starting the next column, with a down arrow within a pair and a connector to the next pair. A same-day follow-up (`0a263a6`, not part of this session) corrected that connector from a plain right arrow — which visually pointed at the *bottom* card of the next pair, silently skipping the actual next chronological club — to an up-right diagonal arrow pointing at the correct top card.

The owner reported that even with the corrected connector, the result still read as confusing: a repeating down-then-diagonal zigzag, unlike every other part of the app (including mobile's own career grid), which reads in the ordinary left-to-right, wrap-to-the-next-row order a person already uses for any grid of things. They asked for exactly that: left to right, wrapping down at the right edge, capped at two rows, and only then a horizontal scroll for whatever doesn't fit.

Plain CSS Grid can't do this directly. Row-major auto-placement (`grid-auto-flow:row`, the default) has no way to cap the row count and redirect overflow sideways — it just keeps adding implicit rows forever, which is exactly ADR 0016's original desktop behavior and the reason ADR 0017 existed. Column-major placement (`grid-auto-flow:column`) caps rows the way ADR 0017 wanted, but reading order becomes column-major (down, then across) instead of row-major (across, then down) — that's the zigzag the owner didn't want, arrow direction aside.

## Decision

- `renderCareer()` now groups a player's clubs into pages of up to eight (a 4x2 block) as it builds the DOM: every eighth club starts a new `<div class="timeline-page">`, appended to `#timeline` (now a plain `<div>`, not an `<ol>` — the native list semantics were already redundant with `.club-step`'s aria-hidden numbering and the region's own `aria-label`, and a non-`<li>` wrapper as a direct `<ol>` child would have been non-conforming markup).
- Each page is an **ordinary row-major 4-column grid** — the exact same layout mobile already uses, just capped at two rows because a page never holds more than eight clubs. `.club:nth-child(4n):after{content:none}` (previously mobile-only) is now unconditional: it suppresses the connector at the end of every row — or every page — the same way this app already suppressed it at mobile row-ends before any of this paging existed. Since `:nth-child` counts siblings within each club's actual DOM parent (its page), this one rule is automatically correct per page at any width, with no page-boundary special-casing needed.
- **Mobile** (`@media(max-width:800px)`): `.timeline-page{display:contents}` makes the wrapper invisible to layout, so every club still flows into one continuous four-column grid that grows to as many rows as the career needs — pixel-identical to ADR 0016, unchanged.
- **Desktop** (`@media(min-width:801px)`): `.timeline-page{display:grid;grid-template-columns:repeat(4,150px);grid-template-rows:repeat(2,auto)}`, and `.timeline{display:flex}` lays pages out side by side. A career longer than one page just adds another page to the row; `.timeline-scroll`'s real horizontal scrollbar (unchanged from ADR 0017) reaches whatever doesn't fit at the current width. No connector is drawn across a page boundary — same "no arrow at a row end" convention as everywhere else, and it avoids reintroducing exactly the kind of misleading-target arrow the `0a263a6` follow-up had to correct once already, just at page scale instead of pair scale.
- All zigzag-specific CSS is removed: `grid-auto-flow:column`, the `↓`/`↗` content rules, and their positioning. The base `.club:not(:last-child):after{content:"➜";top:32px;right:-24px;font-size:18px}` rule (already correctly sized for desktop's 79px crests) now applies on desktop exactly as originally, with no override needed.
- `tests/career-arrow-checks.js` and `tests/career-arrow-layout.test.mjs` (added by the `0a263a6` follow-up to pin the zigzag's arrow directions) are rewritten for the row-major design: same Diego Milito six-stop fixture, now asserting the identical arrow sequence (`➜,➜,➜,none,➜,none`) at both mobile and desktop widths, plus a longer-than-one-page fixture asserting at least two `.timeline-page` elements, genuine horizontal overflow, and no connector at the page-8 boundary. `tests/browser-checks.js` and `tests/game-loading-checks.js`'s `#timeline li` selectors are updated to `#timeline .club` (no longer a `<li>`).

## Consequences

- Verified in a real browser: Diego Milito's six-club career (one page) renders as a plain two-row, left-to-right grid with `➜` connectors, arrow suppressed at the row wrap (position 4) and the end (position 6) — no diagonal anywhere. The longest career (more than one page) renders as two four-column pages side by side, genuine horizontal overflow at 1440px, and no connector at the page-8 boundary. Mobile at 375px produces the identical arrow sequence to desktop for the same fixture, confirming the reading order is now consistent across every width — the thing the previous two attempts didn't quite land.
- `renderCareer()`'s DOM shape changed (page-wrapper `<div>`s, `.club` is now a `<div>` instead of an `<li>`) but the model, scoring, hints and chronological club order are untouched — this is a pure DOM/CSS presentation change, same as ADR 0016 and 0017 before it.
- Two pre-existing, environment-specific browser-driver issues were confirmed unrelated by reproducing them against the unchanged pre-redesign commit: `mobile-language-checks.js`'s all-image `decode()` `EncodingError` (already documented in TESTING.md as of `0a263a6`, same day) and a `game-loading-checks.js` mocked-SDK timing assertion. Neither is caused by this change.
