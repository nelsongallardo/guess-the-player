# 24. A one-time, mandatory nickname prompt at first sign-in

Status: Accepted — implemented 2026-09-28. Amends [ADR 0007](0007-automatic-animal-aliases-and-optional-nicknames.md) and [ADR 0019](0019-suggest-google-name-as-nickname.md), which stay in effect for every sign-in *after* this prompt has been completed once.

## Context

A signed-in account gets a random animal alias immediately and silently (ADR 0007 - `Falcon-a71ea462`-style), and the only way to change it is to find the optional nickname field inside Account. In practice most players never open that screen: they sign in, start playing, and never notice there was a name to pick. The owner asked for this directly, citing Reddit's own signup flow (screenshot: a modal titled "Crea tu nombre de usuario" appears immediately after signup, pre-filled with a computer-generated suggestion and a shuffle control, with a single "Continuar" button - accepting the suggestion as-is is a valid one-click completion, but the modal cannot be dismissed without confirming something).

## Decision

**Server-tracked, not client-tracked.** A new `ranked_private.accounts.nickname_prompted boolean not null default false` column is the only source of truth for "has this account ever completed the prompt." This is deliberately a new, separate flag rather than reusing `enrolled` (already `true` on the very first insert, before any human has seen a form - see `automatic_animal_alias`'s trigger) or re-deriving "still on the default pattern" from the current nickname on every load (that would re-open the modal every session for a player who deliberately *kept* the suggested animal name, which contradicts "mandatory the *first* time"). A client-only flag (`localStorage`) was rejected too: it wouldn't follow the account to a second device, so someone who already chose a real nickname on their phone would be prompted again on desktop.

**`enroll` sets it, unconditionally.** The prompt's "Continuar" and the existing Account nickname field's "Guardar apodo" both call the exact same `enroll` action; `enroll`'s handler now also sets `nickname_prompted=true` regardless of which of those two entry points called it, or whether the submitted name equals the suggested default or is something the player typed themselves. Either way there is nothing left to prompt for.

**Backfill existing accounts by pattern, not by treating every account as unprompted.** Retroactively defaulting every pre-existing row to `false` would re-surface the prompt for accounts that already picked a real, deliberate nickname through the existing optional flow (a regression - that already satisfies the actual goal). The migration instead backfills `nickname_prompted=true` only for accounts whose current nickname does *not* match the automatic `^[A-Za-z]+-[0-9a-f]{8}$` shape (the same pattern the client already uses as `DEFAULT_ALIAS_PATTERN` for ADR 0019's suggestion gating). Accounts still sitting on an untouched default are left at the new column's `false` default, so they see the prompt once on their next load - the same experience a brand-new signup gets, which is exactly the goal this ADR is solving for, not just something to apply going forward.

**Suggested value is the existing animal alias, not the Google name.** ADR 0019 already offers the player's Google name as an editable suggestion, but only inside Account, and never overwrites a name the player already chose. This prompt's own suggestion deliberately stays the animal alias already assigned (consistent with what already shows on the leaderboard) rather than duplicating ADR 0019's Google-name offer in a second place; a "shuffle" control regenerates another animal-shaped suggestion (same `ANIMALS` list and `-`+8-hex-chars format as the server's own `animal_alias_candidate()`) entirely client-side - no round trip, since near-collision with an existing nickname is astronomically unlikely and, if it ever happened, `enroll`'s own uniqueness check would still catch it (the server never trusts a client-generated name blindly).

**Blocking, with no way out except a successful submit.** A plain `<dialog>` opened via `showModal()`, its `cancel` event's default prevented (blocks Escape), no close/X control and no backdrop-click handler wired (native `<dialog>` doesn't close on backdrop click unless a handler adds that). An invalid or taken name shows an inline message and leaves the dialog open for another attempt - the dialog only ever closes on a request that actually succeeds.

**Reuses `enroll` directly, not `RankedUI.mutate('enroll', ...)`.** The existing Account nickname form calls `RankedUI.mutate`, which is deliberately gated to `mode==='ranked'` - it silently no-ops in Daily mode or while still loading. Since this prompt must work regardless of which mode the player happens to be viewing right after sign-in (Daily is the bare-URL default), it calls `Accounts.request({action:'enroll',...})` directly and, on success, re-syncs whichever module (`RankedUI` or `DailyRankedUI`) is currently active to pick up the fresh profile.

**Checked after every response, not just once at boot.** `profile.nicknamePrompted` rides along in every `ranked_private.projection()` and `ranked_private.daily_projection()` response (both gained the field), and both `RankedUI.accept()` and `DailyRankedUI.accept()` - the only two places either module ingests a fresh server response - call the same `NicknamePrompt.maybeOpen(profile)`. This means the prompt reliably appears after the very first successful response following sign-in regardless of mode, without needing a separate "is this truly the first load" signal, and a guard (`isOpen`) keeps a later response from trying to open it a second time while it's already showing.

## Consequences

- Purely additive migration: one new column with a default, a backfill `update`, and `create or replace function` on `ranked_game`/`projection`/`daily_projection` (the same layering convention every prior change to those functions has used) - no `ALTER` narrows any existing constraint, no existing row's `nickname`/`enrolled` value changes.
- No Edge Function code changes were needed: `enroll`'s request/response *shape* is unchanged from the HTTP layer's perspective, only the database-level behavior behind it - so this ships as a database migration alone, unlike ADR 0021's daily-rabona work which also needed a function redeploy.
- A returning player who already has a custom nickname (the overwhelming majority of the backfill, including every account already showing a real name on the live leaderboard) sees no prompt and no behavior change at all.
- The one remaining gap this doesn't close: an account that reaches `enroll` through some future path other than this prompt or the existing Account form would still correctly set `nickname_prompted=true` (the flag lives on the action, not the caller), so no new call site needs to remember to set it separately.
